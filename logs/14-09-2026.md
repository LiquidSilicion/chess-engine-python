# Chess Engine Development Log

**Date:** 14th September 2026  
**Project:** Python Terminal-Based Chess Engine  
**Status:** Core mechanics complete, pre-checkmate/stalemate implementation.

## 📋 Executive Summary
This document summarizes the development of a fully functional, rule-compliant chess engine in Python, built from scratch. The journey started with a basic 2D array board representation and evolved into a robust system featuring complete piece movement validation, special pawn rules (en passant, promotion), castling, and dynamic check detection. This log captures all architectural decisions and implementations up to the point just before checkmate and stalemate detection were added.

---

## 🏗️ Phase 1: Foundation & Board Representation
**Goal:** Create a visual, interactive chess board.
- **Data Structure:** An 8x8 2D list representing the board.
  - **Convention:** Lowercase letters (`p`, `r`, `n`, `b`, `q`, `k`) represent **White** pieces. Uppercase letters (`P`, `R`, `N`, `B`, `Q`, `K`) represent **Black** pieces. `.` represents an empty square.
  - **Orientation:** Row 0 is Rank 8 (Black's back rank), Row 7 is Rank 1 (White's back rank).
- **Coordinate System:** Translated standard algebraic notation (e.g., "e2e4") into 0-indexed array coordinates `(x, y)` using a column mapping dictionary (`{'a': 0, 'b': 1, ...}`) and row math (`8 - int(rank)`).
- **UI:** A `print_board()` function that renders the board with file letters (a-h) and rank numbers (1-8) for easy human readability.

---

## 🔄 Phase 2: Turn Management & Basic Validation
**Goal:** Prevent chaotic gameplay and enforce basic chess etiquette.
- **Turn Tracking:** Introduced a `current_turn` variable alternating between `'white'` and `'black'`.
- **Ownership Validation:** Before any move is processed, the engine checks if the piece at the starting square belongs to the player whose turn it is (using `.islower()` for White, `.isupper()` for Black).
- **Friendly Fire Prevention:** Added logic to reject moves where the destination square contains a piece of the same color.
- **Empty Square Check:** Prevents the player from selecting an empty square as a starting position.

---

## ♟️ Phase 3: Piece Movement Logic
**Goal:** Enforce the unique movement rules of all 6 chess pieces. Implemented in a modular `pieces.py` file.

1. **Knight (`can_knight_move`)**: 
   - Calculated absolute differences `dx` and `dy`. Valid if `(dx==2 and dy==1)` or `(dx==1 and dy==2)`. No path obstruction check needed (knights jump).
2. **King (`can_king_move`)**: 
   - Valid if `max(dx, dy) == 1`. Ensures the king moves exactly one square in any direction.
3. **Rook (`can_rook_move`)**: 
   - Valid if `dx == 0` (vertical) or `dy == 0` (horizontal). 
   - **Path Obstruction:** Implemented a `while` loop stepping from start to destination using `step_x` and `step_y` (±1 or 0), returning `False` if any intermediate square is not `.`.
4. **Bishop (`can_bishop_move`)**: 
   - Valid if `dx == dy` (true diagonal). 
   - **Path Obstruction:** Same stepping logic as the rook, but with `step_x` and `step_y` both being ±1.
5. **Queen (`can_queen_move`)**: 
   - Combined Rook and Bishop logic. Valid if it's a straight line OR a true diagonal. Path obstruction logic dynamically adapts based on the direction.
6. **Pawn (`can_pawn_move`)**: 
   - **Directional Logic:** White pawns move "up" (`dy = -1`), Black pawns move "down" (`dy = +1`).
   - **Case A (Normal):** 1 square forward, destination must be empty.
   - **Case B (First Move):** 2 squares forward, allowed only from starting rank (Row 6 for White, Row 1 for Black), both intermediate and destination squares must be empty.
   - **Case C (Capture):** 1 square diagonally forward, destination must contain an enemy piece.

## ✨ Phase 4: Special Pawn Rules
**Goal:** Implement the two most complex pawn-specific chess rules.

1. **Pawn Promotion**:
   - Triggered immediately after a successful pawn move if it reaches Row 0 (White) or Row 7 (Black).
   - Prompts the user via terminal input to choose a promotion piece (`q`, `r`, `b`, `n`), defaulting to Queen if invalid input is given.
2. **En Passant**:
   - **State Tracking:** The `play_game` loop stores `last_move` as a tuple: `(x1, y1, x2, y2, piece)`.
   - **Detection:** If the current piece is a pawn, and `last_move` was an enemy pawn moving exactly 2 squares (`abs(y1 - y2) == 2`), and the current pawn is adjacent to the destination of that last move, `is_en_passant` is flagged `True`.
   - **Execution:** The moving pawn goes to the diagonal square, and the captured pawn is explicitly removed from the board at `last_move`'s destination coordinates.

## 🛡️ Phase 5: Check Detection & Illegal Move Prevention
**Goal:** Ensure players cannot make moves that leave their own king under attack.

1. **`is_square_attacked(board, x, y, attacker_color)`**:
   - Iterates through the entire board. For every piece belonging to `attacker_color`, it checks if that piece's movement rules allow it to reach `(x, y)`. 
   - *Crucial nuance:* Pawns are handled specially here, checking only their diagonal attack squares, not their forward movement squares.
2. **`is_in_check(board, color)`**:
   - Locates the king of the specified `color`.
   - Calls `is_square_attacked` using the *opponent's* color as the attacker.
3. **Move Validation Integration (`make_move`)**:
   - **The "Make and Undo" Pattern:** Before finalizing a move, the engine:
     1. Saves the state of the starting and destination squares.
     2. Temporarily executes the move on the board.
     3. Calls `is_in_check(board, current_turn)`.
     4. If `True`, it prints an error, **undoes the move** by restoring the saved state, and rejects the input.
     5. If `False`, the move is finalized, and a "Check!" warning is issued if the *opponent's* king is now attacked.

## 🏰 Phase 6: Castling Mechanics
**Goal:** Implement the special king-and-rook maneuver with all FIDE rule constraints.

1. **State Tracking**: Introduced four boolean flags: `white_kingside`, `white_queenside`, `black_kingside`, `black_queenside` (all default `True`).
2. **`update_castling_rights`**: A function called after *every* move. It sets the relevant flags to `False` if:
   - The King moves.
   - A Rook moves from its starting square.
   - A Rook is captured on its starting square.
3. **`is_castling_move`**: Detects if the player is attempting to castle by checking if a King piece is moving exactly 2 squares horizontally (`abs(x2 - x1) == 2` and `y1 == y2`).
4. **`can_castle` Validation**: Checks all FIDE conditions:
   - Castling rights for that specific side are still `True`.
   - The King is **not** currently in check.
   - The path between the King and Rook is completely empty (`.`).
   - The squares the King *passes through* and *lands on* are **not** under attack by the opponent (verified via `is_square_attacked`).
5. **`execute_castling`**: If valid, moves the King 2 squares, and teleports the corresponding Rook to the square immediately adjacent to the King on the opposite side.

## 🏛️ Architectural Highlights
- **Modular Design:** Separated movement logic (`pieces.py`), game rules/validation (`game_rules.py`), and the main game loop/UI (`board.py`).
- **Fail-Fast Validation:** The `make_move` function checks conditions in order of computational cheapness (e.g., empty square check → turn check → piece movement pattern → path obstruction → check detection).
- **UCI Compliance:** The engine natively understands Universal Chess Interface (UCI) notation (e.g., `e2e4`, `e1g1`), making it compatible with future GUI or AI integrations.

## 🚧 Next Steps (Post-Log)
The engine currently allows the game to continue indefinitely even if a player is in check with no legal moves. The immediate next phase of development involves:
1. Generating all pseudo-legal moves for a player.
2. Filtering them through the "Make and Undo" check pattern to find strictly **legal moves**.
3. Implementing **Checkmate** (in check + 0 legal moves) and **Stalemate** (not in check + 0 legal moves) detection.
4. Adding draw conditions: 50-move rule, threefold repetition, and insufficient material.
