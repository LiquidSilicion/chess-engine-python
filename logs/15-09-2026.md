## 🎯 Phase 7: Attack Detection Foundation
**Goal:** Build the foundational function that answers "Can any piece of color X attack square Y?"

### The Algorithm: `is_square_attacked(board, x, y, attacker_color)`
- Iterates through all 64 squares of the board.
- For each piece belonging to `attacker_color`, asks: "Could this piece legally reach (x, y)?"
- Reuses the existing movement functions (`can_knight_move`, `can_rook_move`, etc.) as attack detectors.

### Critical Insight: Pawn Attack Asymmetry
Pawns are the only piece where **movement ≠ attack**. A pawn moves forward but attacks diagonally. Therefore:
- The function **cannot** use `can_pawn_move` for pawn attack detection.
- Instead, it manually calculates the two diagonal attack squares based on pawn color:
  - White pawns (lowercase) attack at `(col±1, row-1)`
  - Black pawns (uppercase) attack at `(col±1, row+1)`

### Why This Matters
This single function becomes the backbone for **check detection, castling validation, and checkmate detection**. Every advanced feature depends on it.

## ⚠️ Phase 8: Check Detection & Integration
**Goal:** Detect when a king is under attack and prevent illegal moves that leave the king exposed.

### `is_in_check(board, color)`
1. Scans the board to find the king of the specified color.
2. Determines the opponent's color.
3. Calls `is_square_attacked(board, king_x, king_y, opponent_color)`.
4. Returns `True` if the king's square is under attack.

### Integration into `make_move`: The "Make-Test-Undo" Pattern
This is the most elegant algorithmic pattern in the entire engine:

```
1. SAVE the state of start and destination squares
2. MAKE the move on the board
3. TEST: Is my king now in check?
   - If YES → UNDO the move, reject input, print error
   - If NO → keep the move, check if opponent is now in check
```

### Why This Pattern is Powerful
- **No special-case code needed:** Instead of writing complex logic for each piece type ("how does moving this rook expose my king?"), we simply simulate the move and ask the existing check-detection system.
- **Handles pins automatically:** A pinned piece (e.g., a bishop blocking a check on the king) is naturally prevented from moving because the "make-test-undo" pattern will detect the exposed king.
- **Scales cleanly:** Adding new piece types or rules doesn't require rewriting check logic.

## 🧮 Phase 9: Legal Move Generation
**Goal:** Generate a complete list of all legal moves for a player — the foundation for checkmate/stalemate detection.

### Two-Stage Filtering Process

**Stage 1: Pseudo-Legal Move Generation (`is_valid_piece_move`)**
- A dispatcher function that routes to the correct movement validator based on piece type.
- For every piece of the current player, tries all 64 destination squares.
- Filters out moves that violate piece-specific rules (wrong pattern, path blocked, capturing own piece).

**Stage 2: Legal Move Filtering (`get_all_legal_moves`)**
- For each pseudo-legal move:
  1. Save board state
  2. Make the move
  3. Call `is_in_check(board, color)` — if the king is in check, the move is illegal
  4. Undo the move
- Collects all moves that pass both stages.

### Performance Note
This function is **computationally expensive** — it simulates every possible move and runs check detection on each. For a typical mid-game position with ~30 legal moves, this means ~30 full board scans. This is acceptable for a terminal game but would need optimization (alpha-beta pruning, move ordering) for a competitive AI.

## 🏁 Phase 10: Checkmate & Stalemate Detection
**Goal:** Detect the two most important game-ending conditions.

### `is_checkmate(board, color)`
```
Return True IF:
  - The player is currently in check
  - AND there are zero legal moves available
```

### `is_stalemate(board, color)`
```
Return True IF:
  - The player is NOT in check
  - AND there are zero legal moves available
```

### Integration into `play_game`
After every successful move, the engine:
1. Determines the opponent's color.
2. Checks for checkmate → prints winner, breaks game loop.
3. Checks for stalemate → prints draw, breaks game loop.

### Key Design Decision
Checkmate/stalemate detection runs **after** the move is completed and the turn has switched. This ensures we're evaluating the position from the perspective of the player who must now respond.

## 🏰 Phase 11: Castling Implementation
**Goal:** Implement the only chess move that involves two pieces simultaneously, with all FIDE rule constraints.

### State Tracking: Castling Rights
Four boolean flags track whether each side can still castle:
- `white_kingside`, `white_queenside`
- `black_kingside`, `black_queenside`

These are passed through the entire call chain (`play_game` → `make_move` → `update_castling_rights`) and updated after every move.

### `update_castling_rights`: The Rights Tracker
Called after every move, sets flags to `False` when:
- A king moves (loses both castling rights for that color).
- A rook moves from its starting square (loses that side's right).
- A rook is **captured** on its starting square (opponent's capture also destroys castling rights).

### `is_castling_move`: Detection
Identifies a castling attempt by checking:
- The piece is a king.
- It moves exactly 2 squares horizontally (`abs(x2 - x1) == 2`).
- It stays on the same rank (`y1 == y2`).

### `can_castle`: Full FIDE Validation
Checks all five conditions:
1. **Rights exist** for the chosen side.
2. **King is not currently in check.**
3. **Path is clear** — all squares between king and rook are empty.
4. **King doesn't pass through** an attacked square.
5. **King doesn't land on** an attacked square.

Conditions 4 and 5 are verified using `is_square_attacked` for each relevant square.

### `execute_castling`: Two-Piece Movement
Moves the king 2 squares, then teleports the rook to the square immediately adjacent to the king on the opposite side. This is the only function in the entire engine that modifies two pieces in a single operation.

## 🤝 Phase 12: Draw Conditions
**Goal:** Implement the three draw conditions beyond stalemate.

### 1. Insufficient Material (`is_insufficient_material`)
Detects positions where neither side can possibly deliver checkmate:
- **King vs King** — obvious draw.
- **King + minor piece vs King** — Knight or Bishop alone cannot force mate.
- **King + Bishop vs King + Bishop (same-color bishops)** — bishops on same-colored squares cannot coordinate to trap a king.

The algorithm:
1. Collects all non-king pieces for each side.
2. If either side has a Queen, Rook, or Pawn → sufficient material (return False).
3. Otherwise, checks specific combinations (K vs K, K+N vs K, K+B vs K, K+B vs K+B with same-color bishops).

### 2. Threefold Repetition (`is_threefold_repetition`)
Detects when the same position occurs three times (not necessarily consecutively).

**Implementation:**
- `get_board_hash(board, current_turn)` creates a hash from the entire board state plus whose turn it is.
- `position_history` list stores every position hash after each move.
- After each move, counts occurrences of the current position in the history.
- If count ≥ 3 → draw.

**Why include the turn in the hash?** Because the same piece configuration with different sides to move is a fundamentally different position (e.g., zugzwang situations).

### 3. 50-Move Rule (`is_50_move_rule`)
If 50 consecutive full moves (100 half-moves) pass without:
- A pawn moving, OR
- A piece being captured

...the game is a draw.

**Implementation:**
- `fifty_move_counter` tracks half-moves.
- Resets to 0 on any pawn move or capture.
- Increments otherwise.
- When it reaches 100 → draw.

The captured piece information is threaded through `make_move`'s return value (6th element of the tuple) to enable this tracking.

## 🏛️ Architectural Evolution

### Data Flow Complexity Growth
The `make_move` function evolved from a simple move executor into a complex state machine:
- **Input:** 8 parameters (board, move string, turn, last move, 4 castling rights)
- **Output:** 6-tuple (move info, 4 updated castling rights, captured piece)
- **Side effects:** Modifies board in place, may trigger promotion prompts

### The Return Value Pattern
To thread state through the call chain without global variables, `make_move` returns a tuple containing:
1. Move coordinates + piece (for en passant tracking)
2. Four castling rights flags (updated)
3. Captured piece (for 50-move rule)

This pattern keeps the code functional and testable, avoiding hidden state mutations.

### Separation of Concerns
- **`pieces.py`** — Pure movement geometry (no game state awareness)
- **`game_rules.py`** — Game-state-aware validation (check, legal moves, draws)
- **`board.py`** — Orchestration, UI, state management
